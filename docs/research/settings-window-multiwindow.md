## 1. Can the Settings window be modal relative to main?

Tauri has no `modal: true` option. On Windows you get a modal window from two pieces, the same way Win32 dialog boxes do it:

1. **Owner.** `WebviewWindowBuilder::parent(&main)` (Rust) or `parent: "main"` (JS `WebviewWindow` options). On Windows this sets an owner, not a child window.
   - `tauri-2.11.5/src/webview/webview_window.rs:617-631`: "**Windows**: This sets the passed parent as an owner window to the window to be created." There is also a Windows-only `owner(&WebviewWindow)` / `owner_raw(HWND)` (lines 633-660) that does the same thing.
   - JS: `WindowOptions.parent?: Window | WebviewWindow | string` (`@tauri-apps/api/window.d.ts:1700`). The string is a label, resolved in `tauri-2.11.5/src/window/mod.rs:277-282` (`config.parent` -> `builder.parent(&window)`).
   - tao creates it as `WS_POPUP` with the owner HWND passed to `CreateWindowExW`, and it skips the `ON_TASKBAR` flag (`tao-0.35.3/src/platform_impl/windows/window.rs:1151-1167`, `1245-1258`). `ON_TASKBAR` is what adds `WS_EX_APPWINDOW` (`window_state.rs:258-259`).
   - Not behind a feature flag in 2.11.5. (In #1643 a maintainer said it needed the `unstable` flag at the time. In the pinned source `parent()` has no `cfg` gate.)
   - Win32 owned-window rules ([MSDN, Owned Windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#owned-windows)): always above its owner in z-order, destroyed when the owner is destroyed, hidden when the owner is minimized.
2. **Disable the owner.** `WebviewWindow::set_enabled(false)` on main (Rust), or `setEnabled(false)` in JS (since 2.0.0, PR [#11154](https://github.com/tauri-apps/tauri/pull/11154), closes [#6660](https://github.com/tauri-apps/tauri/issues/6660)). On Windows it is a plain `EnableWindow(hwnd, enabled)` (`tauri-runtime-wry-2.11.4/src/window/windows.rs:13-15`).
   - A disabled window gets no keyboard or mouse input ([MSDN, Disabled Windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#disabled-windows)). Disabling the top-level window also covers the WebView2 child HWND. MSDN says child input goes to the parent only when the child itself is disabled. The general rule is that a disabled parent blocks its descendants. Unverified against WebView2 specifically.
   - **Order matters:** re-enable the owner *before* the modal window is destroyed. Otherwise Windows can't hand activation back to the disabled owner and activates some other app's window ([Raymond Chen, "The correct order for disabling and enabling windows"](https://devblogs.microsoft.com/oldnewthing/20040227-00/?p=40463)). In Tauri, do it in the Settings window's `WindowEvent::CloseRequested`, which runs before the destroy.
   - JS permission: `core:window:allow-set-enabled` is **not** in `core:default` (see the list in `tauri-2.11.5/permissions/window/autogenerated/reference.md`). Calling it from Rust needs no permission.

macOS turns `set_enabled(false)` into an attached sheet (`tauri-runtime-wry-2.11.4/src/window/macos.rs:12-37`). That doesn't matter for us on Windows, but it behaves differently.

Prior requests: [#1643](https://github.com/tauri-apps/tauri/issues/1643) (child windows, "now supported in v2"), [#5051](https://github.com/tauri-apps/tauri/issues/5051) (modal, closed as a duplicate of #1643). There is no first-class modal API.

**Main hidden to tray, Settings opened from the tray menu:**
- The owner relationship works on a hidden owner. Per MSDN, owned windows are hidden only when the owner is *minimized*, not when it is hidden. So Settings shows while main stays hidden. Unverified by running it.
- An owned window gets **no taskbar button**. The Shell adds buttons only for unowned windows ([MSDN, Managing Taskbar Buttons](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar#managing-taskbar-buttons)), and tao doesn't set `WS_EX_APPWINDOW` for owned windows. With main hidden, Settings is reachable only from the screen, Alt+Tab and the tray. Unverified: whether `set_skip_taskbar(false)` (ITaskbarList `AddTab`, `tao .../window.rs:1529-1536`) puts a button back for an owned window.
- Our main window handles minimize by calling `unminimize()` then `hide()` (`src-tauri/src/lib.rs:249-255`). Minimizing main hides owned windows, and restoring main shows them again. So minimizing main while Settings is open probably makes Settings flash off and back on. Unverified. Since main is disabled while Settings is open, the user can't minimize it from its own caption anyway.

**What this means for us:** a modal Settings window on Windows is feasible. Do it in Rust:
`WebviewWindowBuilder::new(app, "settings", WebviewUrl::App("/settings".into())).parent(&main)?.build()?`, then `main.set_enabled(false)`. In the Settings window's `CloseRequested` handler, call `main.set_enabled(true)` and focus main if it is visible. If main is hidden to tray, the window still works but has no taskbar button. That is fine for a short-lived dialog. If we skip the owner and only disable main, Settings gets its own taskbar button but loses "always above main".

## 2. Shared `localStorage` and the `storage` event

- All webviews with the same `data_directory` (default `None`) share one wry `WebContext`. The store is keyed by `data_directory` (`tauri-runtime-wry-2.11.4/src/lib.rs:176`, `4785-4810`). So they share the WebView2 user data folder.
- Every window loads the same app origin (`devUrl` `http://localhost:3000` in dev, the bundled app origin in production). Same origin plus same profile means the same `localStorage` area.
- The `storage` event: by the HTML spec it fires in the *other* documents that share the storage area, never in the one that wrote. For WebView2 I found no primary source either way (no hits in tauri or WebView2Feedback issues). The only tauri reports are Linux/WebKitGTK: [#10981](https://github.com/tauri-apps/tauri/issues/10981) and [#14369](https://github.com/tauri-apps/tauri/issues/14369). There a maintainer and a reporter confirm `localStorage` *syncs* between windows of one process. It does not sync between two separate app processes (we have `tauri-plugin-single-instance`, so that case doesn't arise). **Unverified on WebView2.** Check it with a two-window test before relying on it.
- `ui/src/themes/storage.ts` already listens for `storage`, but it only drops its cache (`cachedPreferences = null`). It doesn't re-apply the theme. Even if the event fires, main won't repaint until something re-reads the preferences.

**What this means for us:** the Settings window will read the same theme from `localStorage`. To make a theme change show up live in main, don't rely on the `storage` event alone. Either add a `storage` listener that re-applies the theme (if the WebView2 test passes), or emit an explicit Tauri event (`emitTo("main", "theme:changed", ...)`) and have main re-read. The event works whatever WebView2 does.

## 3. `emit` / `emit_to`

- Rust `Emitter::emit` "Emits an event to all targets" (`tauri-2.11.5/src/lib.rs:933-950`). Every webview's JS listeners get it, plus Rust listeners.
- Rust `emit_to(target, ...)`: a `&str` becomes `EventTarget::AnyLabel`, matching any window/webview/webviewWindow with that label (`lib.rs:959-981`). The filter is in `src/manager/mod.rs:604-638`.
- JS `emit(event, payload)` goes to all targets. `emitTo(target, event, payload)` takes a label string (becomes `{kind: 'AnyLabel'}`) or an `EventTarget` (`@tauri-apps/api/event.d.ts:115-145`, `event.js:152`).
- **Gotcha (from source, not runtime-tested):** a JS listener registered with the plain `listen()` from `@tauri-apps/api/event` defaults to target `{kind: 'Any'}` (`event.js:74-75`). `match_any_or_filter` returns `true` for an `Any` listener whatever the emit target (`tauri-2.11.5/src/event/listener.rs:305-311`), and `emit_filter` walks every webview (`manager/mod.rs:577-581`). So `emit_to("settings", ...)` **still reaches a plain `listen()` in main**. Only listeners registered with a target, e.g. `getCurrentWebviewWindow().listen(...)`, are actually scoped. The docs page ([Calling the Frontend from Rust](https://v2.tauri.app/develop/calling-frontend/)) says "Webview-specific events are not triggered to regular global event listeners". That sentence is about Rust `listen` vs `listen_any`, and the JS source behaves as described above.

**What this means for us:** `ui/src/hooks/useTauriEvent.ts` uses the global `listen`. Every existing Rust `app_handle.emit(...)` (`notification:new`, `server:status`, `subscriptions:synced`, ...) will also reach the Settings window if it mounts the same hooks. That is harmless, but the Settings route shouldn't mount notification-list logic. For window-specific traffic, give events distinct names (`settings:*`). Don't rely on `emit_to` alone to hide them from `listen()` in other windows.

## 4. Capabilities for the new window label

- A capability's `windows` field is a list of labels and "Can be a glob pattern". If a label matches, the capability applies to all webviews of that window (`tauri-utils-2.9.3/src/acl/capability.rs:150-163`). There is also a `webviews` field for multiwebview windows.
- The ACL check is keyed only on the calling window/webview label and origin (`tauri-2.11.5/src/webview/mod.rs:1794-1801`). Who created the window, Rust or JS, makes **no difference** to the new window's permissions.
- What differs is the *creator*. Creating from JS needs `core:webview:allow-create-webview-window` on the calling window (we grant it to `main` already). Creating from Rust needs nothing.
- Plugin commands are always ACL-checked. Our own `#[tauri::command]`s are checked only when the app defines an app ACL manifest, or for remote origins (`webview/mod.rs:1819-1850`). `src-tauri/build.rs` is plain `tauri_build::build()`, so every local window can call our commands without listing them.
- `core:default` -> `core:window:default` is read-only (`is-*`, sizes, `title`, `theme`, ...). `show`, `hide`, `set-focus`, `unminimize`, `set-enabled`, `close` are **not** included (`tauri-2.11.5/permissions/window/autogenerated/reference.md`). Any of those called from JS need explicit `core:window:allow-*` entries.

**What this means for us:** add `"settings"` to `windows` in `src-tauri/capabilities/default.json`, next to `main` and `image-preview`. The Settings window then gets `autostart:allow-*`, `notification:*`, `updater:default` and `shell:allow-open`, which the current settings dialog uses. If open/focus/enable/disable live in Rust (recommended below), no new window permissions are needed.

## 5. Restoring/focusing an existing window, Rust vs JS

- The pattern ntfier already uses (`src-tauri/src/lib.rs:139-143`, `189-213`): `app.get_webview_window(label)`, then `show()` and `set_focus()`. A window the user minimized also needs `unminimize()` first. `show()` alone doesn't restore a minimized window (Win32 `ShowWindow(SW_SHOW)` keeps the minimized state; tao maps `Show` to `set_visible(true)`, `tauri-runtime-wry-2.11.4/src/lib.rs:3489`).
- Labels are unique, so "open settings" should be "get or create": if `get_webview_window("settings")` returns `Some`, unminimize, show and focus it. Otherwise build it.
- Known issue in the builder docs (`tauri-2.11.5/src/webview/webview_window.rs:56-59`, `113-116`): "On Windows, this function deadlocks when used in a synchronous command and event handlers" ([wry#583](https://github.com/tauri-apps/wry/issues/583)). Use an `async` command. The tray menu case was fixed back in v1 ([#3110](https://github.com/tauri-apps/tauri/issues/3110), "Creating a new window through a menu event handler results in app freeze", closed as fixed). Whether building inside `on_menu_event` in 2.11.5 is still safe is unverified. Spawning the open call onto `tauri::async_runtime::spawn` avoids the question.
- The tray menu runs in Rust (`src-tauri/src/lib.rs:177-197`). It currently has only Show and Quit.

**What this means for us:** write one Rust function `open_settings(app: &AppHandle)` (get-or-create, owner = main, `set_enabled(false)` on main, focus). Expose it as an `async` Tauri command for the UI's gear button, and call it from a new tray menu item. One code path, no extra JS permissions, and it works while the webview in main is hidden. JS creation (the `image-preview` pattern in `NotificationAttachments.tsx`) can't be triggered from the tray without a round trip through main's webview. Also make tray "Show", tray left-click and the single-instance callback focus `settings` when it exists. Main is disabled then, and focusing it would leave the user on a window that ignores input.

## 6. Lifecycle: quit, and main hidden to tray

- **Quit** (`app.exit(0)` from the tray): `AppHandle::exit` requests `RunEvent::ExitRequested` then `Exit` (`tauri-2.11.5/src/app.rs:573-580`). The runtime sets `ControlFlow::Exit` (`tauri-runtime-wry-2.11.4/src/lib.rs:4354-4366`). No per-window `CloseRequested` fires, so Settings closes with the process and the re-enable handler doesn't run. That's fine, since nothing survives.
- **Main closed for real** (minimize-to-tray off): Windows destroys owned windows with their owner (MSDN), so Settings goes too. When the last window is destroyed, tauri raises `ExitRequested` and exits (`lib.rs:4310-4325`). Without an owner, closing main would leave the app running with only Settings open. But main is disabled while Settings is open, so the user can't close it from its caption anyway.
- **Main hidden to tray** (`CloseRequested` -> `prevent_close` + `hide`, `src-tauri/src/lib.rs:241-247`): hiding doesn't hide or destroy owned windows. Only minimizing does (MSDN). Closing Settings while main is hidden doesn't exit the app, because the window store isn't empty (main still exists).
- `tauri-plugin-window-state` (registered with defaults, `src-tauri/src/lib.rs:149`) tracks **every** window not on its denylist. It restores size/position/visibility when the window becomes ready and saves on `CloseRequested` (`tauri-plugin-window-state-2.4.1/src/lib.rs:407-450`). Settings would reopen where it was last closed, not centered on main. Use `.with_denylist(&["settings"])` (or `skip_initial_state("settings")`) if we want it centered every time.

**What this means for us:** with an owner, Settings can't outlive main, and quit needs no extra code. The re-enable step must sit in Settings' `CloseRequested`. Decide whether window-state should remember Settings' position.
